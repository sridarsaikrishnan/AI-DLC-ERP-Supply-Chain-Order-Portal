# Phase 3 Code Generation Plan — full async E2E (floci + Terraform + real connections)

Turns the authored-but-unwired pieces into a running async system: api + worker as
separate processes over Postgres + SNS/SQS (floci locally), with Terraform provisioning
and real Odoo connectivity. Each item has a checkbox; marked as completed when its tests
pass (or, for infra, when `terraform validate` / a documented manual step succeeds).

- [x] `catalog/infrastructure/postgres.py` — SQLAlchemy `ItemRepository`
- [x] `tenancy/infrastructure/postgres.py` — SQLAlchemy `BindingRepository`; `add()` maps only `pgcode == 23505` (unique_violation) to `BindingConflict` — an FK violation (unknown connection_id) re-raises as-is, it is not a uniqueness conflict
- [x] `ordering/projections/postgres_store.py` — Postgres `OrderProjectionStore` (orders + order_status_history). `create()` is `ON CONFLICT (order_id) DO NOTHING` — consumers are at-least-once so redelivery of `OrderSubmitted` must not crash the worker. Timeline `occurred_at` uses `.isoformat()` to match the in-memory store's format (GraphQL output must not change with the profile).
- [x] `webhooks_inbound/infrastructure/postgres.py` — `DedupStore` (processed_events) + `OrderLocator` (orders reverse-routing query, read-only)
- [x] repository tables for connections/items/bindings already in migration 0001 — added missing column: `orders.lines` (JSONB) via migration `0002_order_lines`
- **Verified 2026-09-27**: Docker + a working `pip install --trusted-host pypi.org --trusted-host files.pythonhosted.org ...` (bypasses the corporate TLS-interception proxy that blocked plain `pip install` in every prior increment) unblocked a real run. `docker compose up -d postgres && alembic upgrade head && pytest tests/integration/test_postgres_adapters.py` — **5/5 pass**. Full suite `pytest src tests` — **72/72 pass** (no regressions).
- **Carried to item C**: `set_state` still inserts a fresh `order_status_history` row on every call with no dedupe — a redelivered non-`OrderSubmitted` event (e.g. `OrderConfirmed`) will double the timeline. C's consumers must dedupe on `event_id` via `processed_events` *before* calling the projector; the projector/store itself should not have to be idempotent for every event type.
- **New Phase 3 open item (not fixed here, needs B/G)**: migration 0001 enables RLS on `orders`/`order_status_history` but no adapter calls `bind_tenant`; it only worked in ad hoc testing because `portal` is the table owner (RLS-exempt). Under a real non-owner app role, projector inserts get rejected (no `app.tenant_id` set) and `PostgresOrderLocator`/operator reads return nothing. B must give the worker/ingress a role that bypasses RLS (or owns the tables) and have reseller-facing reads call `bind_tenant`.

## B. Composition profile (select infra by settings) — DONE, verified against real Postgres + the real FastAPI app
- [x] `composition.build_container(settings)` — profile comes from `Settings.profile` (env `APP_PROFILE`, default `"memory"`); `memory` (unchanged) and `postgres` profiles
- [x] `postgres` profile wires: `PostgresEventStore` + Postgres repos/projection store + real/stub `OdooAdapter` (per `ERP_ODOO_MODE`) + `SecretsManagerSecretStore`. **Deviation from the checklist wording, intentional**: the repo is built `EventSourcedRepository(event_store, Order)` — **no** `SnsFifoPublisher` passed as `publisher`. `PostgresEventStore.append` already writes the outbox row in the same DB transaction as the event; if the repo also published synchronously, every event would be delivered twice (once here, once by the relay). The publisher belongs in the relay (`worker/main.py`, item C) — don't "fix" this by wiring one into the repo.
- [x] `api/app.py` uses the configured profile (`build_container()` reads `Settings.profile` itself, no call-site change needed). Dropped inline `run_until_empty`: `Container` now has a `drain()` field (memory: `bus.run_until_empty`; postgres: no-op — the worker drains). Updated **three** call sites, not the one the checklist named — `webhooks.py`, and (found by grepping `src/api src/worker` for `.bus`/`run_until_empty` after an advisor review) both mutations in `graphql/reseller/schema.py` (`placeOrder`, `cancelOrder`), which would have thrown `AttributeError` on `None.run_until_empty()` under the postgres profile.
- **Two pre-existing bugs surfaced by actually running the app** (neither introduced by B; the app had never been run end-to-end before this — worth flagging since they'd have blocked *any* future work here, not just B's):
  - `boto3.client(...)` calls in `SecretsManagerSecretStore`, `SnsFifoPublisher`, `SqsConsumerRunner` (`shared/secrets/store.py`, `shared/messaging/aws.py`) never passed `region_name`, so building a client with no `AWS_REGION` in the environment raised `NoRegionError` immediately. Fixed by threading `settings.aws_region` through all three constructors + the one existing call site in `worker/main.py`.
  - `GraphQLContext` (`api/graphql/context.py`) didn't inherit from `strawberry.fastapi.BaseContext`, so strawberry's FastAPI integration rejected it (`InvalidCustomContext`) the moment a real GraphQL request hit the app. One-line fix: `class GraphQLContext(BaseContext)`.
- **Debt, not fixed (low priority, doesn't block anything)**: `Settings.database_url` is dead in the postgres profile — `shared/persistence/engine.py` reads `DATABASE_URL` from the environment directly rather than through `Settings`, so a `Settings` built with a different `database_url` is silently ignored. Harmless today (both read the same env var); threading it through `engine.get_engine()` is optional cleanup, not correctness.
- **Verified 2026-09-27**: `tests/integration/test_postgres_composition.py` (container built directly, profile=postgres: seed → place_order → manually drive `order_processor`/`order_projector` the way the worker will → Postgres-backed projection shows `Validated`) and `tests/integration/test_app_profiles.py` (the *actual* FastAPI app via `TestClient` under both profiles — memory profile POSTs a `placeOrder` GraphQL mutation and gets `"Sent to ERP"` back; postgres profile POSTs the same mutation, gets no exception, and leaves exactly one `OrderSubmitted` event + one unpublished outbox row for the worker to pick up, with the projection correctly still empty). Both tests clean up their own event/outbox/order rows so they don't leave stale work for item C's first relay run. `pytest src tests`: **75/75 pass**, run twice back-to-back to confirm no leftover-state flakiness.

## C. Worker wiring (the async consumers) — DONE, verified live end-to-end (floci + real worker + real API process)
- [x] `worker/main.py` — one `SqsConsumerRunner` per queue (`order-processing`, `order-delivery`, `projections`) → `container.order_processor.handle` / `container.delivery_handler.handle` / `container.order_projector.handle`, all on the `postgres` container. **`webhook-dispatch` intentionally has no consumer** — messaging-topology.md's own resolved decision is that outbound webhooks are optional/secondary (off by default; GraphQL is primary) and no `webhook_dispatch` handler was ever built. `scripts/messaging_bootstrap.py` still provisions the queue/DLQ so turning it on later is additive.
- [x] each handler wrapped with `_dedupe()` (`processed_events(consumer, event_id)`, checked before calling the handler, marked only after it returns without raising) — this is item A's carried-forward note, now actually implemented rather than deferred again.
- [x] `RelayRunner` + `ReconcileScheduler` threads started; `ReconcileScheduler` gets `open_orders_provider` via a small raw-SQL query (`orders` where not terminal) — no existing port covered this query shape, and a whole new port felt like more machinery than a 10-line SELECT warranted.
- [x] graceful shutdown (SIGTERM/SIGINT → `threading.Event`) + structured logging (`logging.basicConfig`, per-module loggers)
- **Not built, deliberately deferred**: per-connection circuit breaker. A transient ERP failure already raises `DeliveryRetry`, which SQS's redrive/backoff turns into bounded retries — that's baseline resilience. A breaker that trips *per connection* and short-circuits without even calling the ERP is real, separable follow-up work (needs a decision on trip/reset thresholds), not required to get the pipeline running.
- **Bugs found and fixed while getting this to actually run** (none of this code had ever executed before — see the log below for how each was found):
  1. **Thread-killing bug in `SqsConsumerRunner.poll_once`** (`shared/messaging/aws.py`, pre-existing, not introduced by C): an unhandled handler exception propagated out of the polling loop, permanently killing that queue's consumer thread — not just failing one message. Fixed: catch per-message, log, leave undeleted for SQS redrive, continue polling. The same bug shape existed in `RelayRunner.run_forever` (one bad relay pass would stop the relay forever) and `ReconcileScheduler.run_forever` (one connection's failure would stop the sweep for every other connection) — fixed both the same way, since it's the same root cause in three sibling `run_forever` loops.
  2. **GraphQL types constructed with positional args** (`api/graphql/reseller/schema.py`, `api/graphql/operator/schema.py`, pre-existing): `OrderLineType(l.product_key, l.quantity, l.unit_of_measure)` raised `takes 1 positional argument but 4 were given` — strawberry types require keyword args. Never caught before because no test ever actually queried an order back through GraphQL (only checked `container.projections` directly). Fixed both call sites; added a regression test (`tests/integration/test_app_profiles.py`) that queries the order through the real GraphQL resolver, not just the container.
  3. **Duplicate timeline entries** (`ordering/projections/store.py` + `postgres_store.py`): `OrderState.VALIDATED` and `OrderState.READY_FOR_DELIVERY` both map to the reseller-facing label "Validated" (by design), but each got its own timeline row, so resellers saw "Validated" twice in a row a few hundred ms apart. Fixed: `set_state` now skips appending when the new label matches the immediately-preceding one, in both stores.
- **Test-pollution incident, resolved by user decision**: dozens of earlier `pytest` runs (items A/B) had left ~60 stray `erp_connections` and ~32 stray `orders` rows in the shared local dev Postgres, because 3 of the test functions created rows but never cleaned them up. The first-ever `RelayRunner` run relayed all of it at once, and the worker choked on stray connections with bogus `secret_ref`s. Asked the user how to clean up (a scripted mass `DELETE` was correctly blocked by the sandbox's safety classifier); user chose `alembic downgrade base && alembic upgrade head`. Also fixed the 3 test functions themselves to clean up their own connection/item/binding rows so this doesn't recur.
- **Live verification (2026-09-27)**: `docker compose up -d postgres floci`, `scripts/messaging_bootstrap` (topic + 4 FIFO queues + DLQs), a floci Secrets Manager secret for the demo Odoo connection, `scripts/seed_demo`, worker + API started as real local processes (`APP_PROFILE=postgres`, `ERP_ODOO_MODE=stub`). Placed 3 orders via real HTTP `placeOrder` GraphQL mutations against the running API; each one flowed through the full async chain (outbox → SNS FIFO → SQS FIFO → order-processing → order-delivery (stub ERP) → projections) and came back `"Sent to ERP"` on a GraphQL query, with a clean 3-entry timeline. Worker survived a redriving stale message without dying (the fix for bug 1, confirmed live). `pytest src tests`: 75/75 pass, run repeatedly including once with the worker live against the same database, no new leaks.

## D. Inbound webhook auth (Odoo reality) — DONE, verified live (real HTTP POST against the running demo)
- [x] shared-secret-in-path verification path for Odoo; kept HMAC for ERPNext (unchanged route, unchanged behavior). `webhooks_inbound/domain/signature.py` gained `verify_shared_secret` (constant-time compare of the raw secret, not an HMAC digest); `WebhookAuthMode` enum on `InboundWebhook` (`HMAC` | `SHARED_SECRET`) selects which check `InboundWebhookService.handle()` runs.
- [x] **Separate secret, not reused**: added `ErpConnection.webhook_secret_ref`, distinct from `secret_ref` (the ERP login credential) — migration `0003_webhook_secret_ref`. target-architecture.md §6 already called these out as different secret categories ("`erp_connections.secret_ref` **and** inbound-webhook signing keys"); reusing the login credential as a URL-path secret would have meant a leaked webhook URL also leaked ERP login access. `ConnectionWebhookSecretResolver` (composition.py) now resolves `webhook_secret_ref`; `None` (not onboarded) means every webhook for that connection is `401` and it silently relies on the reconcile sweeper, matching target-architecture.md 5a's stated fallback.
- [x] `api/http/webhooks.py` now has two routes: `POST /erp/webhook/{connection_id}` (HMAC header, unchanged) and `POST /erp/webhook/{connection_id}/{webhook_secret}` (new, shared-secret-in-path). Both funnel through one `_dispatch` helper into the same `InboundWebhookService`.
- **Optional IP allowlist — deliberately not built.** No schema field, no admin surface to configure it exists, and nothing is driving the requirement yet (YAGNI). The design doc marks it optional; noted here so it isn't silently forgotten, not silently dropped.
- [x] Odoo Automation Rule setup documented: **`docs/odoo-webhook-setup.md`** (secret provisioning, the Automation Rule's Python code + exact payload shape, a curl to verify it, the security tradeoff of a URL-embedded secret spelled out explicitly). Corrected `docs/local-setup.md` §7, which had claimed a native Odoo "Webhook" action type that doesn't exist in Community edition — links to the new doc instead.
- **Honest scope boundary**: the *receiving* side (our route, auth, attribution, projection) is verified end-to-end — `tests/integration/test_odoo_webhook_shared_secret.py` (correct secret accepted + updates order status, wrong secret rejected) plus a live curl against the running demo (`SO_204adbd7c43c`, 200/401/401 exactly as expected). Actually clicking through Odoo's Automation Rule UI on a live instance and confirming `requests` is importable in its sandboxed `safe_eval` was **not** done this session (no Odoo container was brought up) — flagged in the doc itself, not glossed over.
